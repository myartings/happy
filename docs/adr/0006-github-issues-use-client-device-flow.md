# ADR 0006: Use client-side Device Flow for GitHub Issues

## Status

Accepted for implementation on 2026-08-09. Supersedes the authentication,
credential-storage, and transport portions of ADR 0005.

## Context

The personal Happy client includes a small GitHub Issues UI, but the first
implementation sends every Issue operation to personal routes on the Happy
server. The official Happy server does not provide those routes. Consequently,
an otherwise valid official Happy login receives `404 Not Found`, and using the
feature requires operating a personal server for a narrow, client-owned feature.

The maintenance goal is stronger than merely making the current route work:

- Happy's official account, sync, and GitHub profile behavior must remain
  unchanged.
- The personal feature should stay isolated enough to merge future upstream
  changes into personal `main` with small, obvious host seams.
- No GitHub App private key or client secret may be shipped in a client.
- Access must remain limited to Metadata read and Issues read/write on
  repositories selected during GitHub App installation.
- Desktop and mobile credentials must not use browser storage, MMKV, Happy sync,
  logs, or the Happy server.

GitHub App Device Flow exchanges a public client ID and a short-lived device
code for a user access token. A client secret is not required for that exchange.
For a token originally generated by Device Flow, GitHub also permits refresh
without a client secret. This makes Device Flow viable for a native public
client while preserving the GitHub App permission intersection.

GitHub cautions that Device Flow has no redirect-URI binding and should be used
only for constrained clients. Happy will enable it only on installed desktop
and mobile clients, where avoiding fragile cross-app callback routing is the
reason for choosing it. Browser Happy is excluded from this decision.

## Decision

### Ownership boundary

GitHub Issues becomes a client-owned Module. It communicates directly with
GitHub and has no runtime dependency on personal Happy server routes. The
existing Happy GitHub profile connection remains a separate official feature;
connecting or disconnecting GitHub Issues must not mutate it.

The Module exposes a small Interface for connection state, repository discovery,
and Issue operations. Device polling, token rotation, API versioning, raw GitHub
payloads, platform transport differences, and secure storage remain private
Implementation details.

### Authentication and permissions

- Use a dedicated GitHub App with Device Flow enabled.
- Request only repository Metadata read and Issues read/write.
- Ship only the public GitHub App client ID and app slug as build configuration.
- Use GitHub App user access tokens, never installation tokens generated from a
  private key.
- Keep expiring user tokens enabled. Refresh five minutes before access-token
  expiry and serialize concurrent refresh attempts.
- Atomically replace the access and refresh tokens after every successful
  refresh because GitHub invalidates the old pair.

The authorization screen displays GitHub's verification URI and user code,
offers Copy and Open GitHub actions, and polls at GitHub's supplied interval.
It handles `authorization_pending`, `slow_down`, expiry, denial, cancellation,
and app misconfiguration without persisting device codes.

### Credential storage seam

Define a `GithubCredentialStore` seam with these Adapters:

- iOS/Android: Expo SecureStore, backed by the platform Keychain/Keystore.
- Tauri desktop: Rust commands backed by the operating-system credential store
  (macOS Keychain, Windows Credential Manager, and Linux Secret Service).
- Tests: an in-memory fake.

There is no browser/localStorage Adapter. Plain browser builds report
`unsupported_platform`, hide the normal feature entry, and reject direct routes
with an explanatory state. Tauri is a supported desktop platform even though
React Native reports it as `web`.

Store one versioned token bundle under an app-variant-specific service/account
key. It contains the access token, optional refresh token, calculated expiries,
token type, schema version, and minimal account identity needed to label the
connection. Repository mappings remain non-secret local settings. Issue content
remains memory-only.

If secure storage is unavailable, authentication fails closed. Tokens must never
fall back to localStorage or another plaintext store. Token values and Device
Flow codes must be redacted from logs and error telemetry.

### GitHub transport seam

Define a `GithubTransport` seam with a native-fetch Adapter, a Tauri HTTP-plugin
Adapter, and a deterministic test fake. Only the transport knows GitHub base
URLs, headers, API versions, and response bodies.

The Module normalizes GitHub responses into the existing Happy-owned repository
and Issue DTOs. It discovers repositories using installations accessible to the
user access token and the repositories accessible through each installation.
When none are available, the UI links to the GitHub App installation page and
refreshes discovery when Happy regains focus.

### Lifecycle and revocation

“Remove from this device” deletes the local token bundle. Full authorization or
installation revocation remains a GitHub settings action, linked from the UI.
The client cannot safely call administrative revocation endpoints that require a
client secret.

Invalid or expired refresh credentials produce `reauthorization_required`.
Transient network, rate-limit, and storage failures preserve the last valid
bundle; definitively invalid credentials are removed only after the error has
been classified.

### Server retirement

Remove the Issue routes, service/runtime, Issue server flag, and Issue-specific
branches in the official GitHub connect flow. Restore the latter to upstream
profile-only behavior. Do not delete the historical Prisma migration that added
Issue token metadata.

After the client path passes live acceptance, add a forward Prisma migration to
drop only the now-unused Issue credential columns and update the schema. This is
a separate cleanup slice so a client rollback does not require recovering
discarded credentials. Preserve unrelated GitHub profile compatibility fixes.

## Consequences

- Happy (dev) can manage Issues while continuing to use the official Happy
  server; no personal always-on Issue service is required.
- Each device authorizes separately. Credentials do not follow the Happy account
  across devices.
- The client owns token-security and GitHub API compatibility responsibilities.
- Desktop adds a small native credential-store Adapter; Linux requires an
  available Secret Service and otherwise fails closed.
- Browser Happy cannot use this v1 feature. Adding browser support would require
  a separate backend or a deliberately reviewed browser-auth design.
- Host coupling is limited to configuration, feature-flagged navigation/routes,
  and platform Adapter registration. Most change remains inside one deep Module.
- Device Flow's phishing tradeoff is explicit: Happy opens only GitHub's official
  verification URL, names the expected app, never asks the user to paste a token,
  and does not enable the flow on general browser clients.

## Rejected alternatives

### Continue running a personal Happy Issue service

Rejected for the current single-user feature because deployment, monitoring,
server upgrades, and availability create more maintenance than the Issue UI.

### Add routes to the official Happy service

Not available for a personal fork and would couple release timing to upstream.

### Store tokens in web localStorage

Rejected because browser storage does not provide the required secret boundary.

### Ship a GitHub App client secret or private key

Rejected because installed clients cannot keep either secret confidential. A
private key would also enable much broader app-level authority.

### Reuse the official Happy GitHub token

Rejected because the official profile connection has different scopes,
ownership, storage, and lifecycle. Silent privilege upgrades would make both
features harder to reason about.

### Web authorization flow with a personal callback service

Rejected for v1 because it recreates the service dependency Device Flow is meant
to remove. It may be reconsidered if browser support becomes a product need.

## Rollback

Turn off the client feature flag and remove the Device Flow Module/Adapters. The
official Happy GitHub profile integration is unaffected. During the staged
rollout, keep server-route removal and schema-column cleanup in separate commits
so either can be reverted independently.
