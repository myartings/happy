# Decisions: `codex-first-happy-client`

| ID | Question | Status | Decision/evidence |
| --- | --- | --- | --- |
| D1 | Is Codex a visual influence or the product baseline? | decided | Codex is the default UI, information-architecture, and interaction baseline. Happy functionality is the hard preservation constraint; deviations require evidence that parity would remove, hide, or degrade a Happy capability. User decision, 2026-08-30. |
| D2 | Where does the Codex-first shell apply? | decided | Globally across Happy Desktop and all Agent backends, not only Codex Sessions and not as a separate optional mode. User selected the recommended global option, 2026-08-30. |
| D3 | Which platform establishes the first accepted result? | decided | Complete and accept macOS first, then adapt the stable contract to Windows. User selected macOS-first, 2026-08-30. |
| D4 | How often is human visual acceptance required? | decided | One final acceptance review after the complete macOS scope. Intermediate milestones use automated checks and durable comparison evidence; pause early only for a material unresolved functionality conflict or missing authority. User decision, 2026-08-30. |
| D5 | What product surface defines the first macOS delivery? | decided | The complete daily-use coding loop, including navigation, Session lifecycle, conversation, composer, tools, approvals, diffs, command surfaces, contextual overlays, side panels, necessary settings, and representative lifecycle states. Low-frequency account, billing, and cloud administration are deferred. User selected the recommended daily-loop scope, 2026-08-30. |
| D6 | How are reference assets handled? | decided | Use current local Codex runtime evidence for observation, keep private screenshots and recordings outside tracked source, and implement original Happy components without copying proprietary reference assets. Existing repository evidence policy plus the new functional contract. |
| D7 | What risk boundary permits autonomous implementation? | decided | Client presentation, local projection, and existing-route composition are cleared with controls. Approval handlers/payloads, authentication, authorization, encryption, synchronization, Server, Machine RPC, Session protocol, data migration, destructive external verification, and public release are outside the cleared boundary. See `risk-assessment.md`. |
| D8 | May work continue on Windows while the macOS console is unavailable? | decided | Yes. The user authorized a Windows ownership transfer on 2026-08-30. Windows may reconstruct the exact dirty source state, extend the already platform-resolved contract to Windows through a new tested slice, build and validate a native Windows package, and continue non-macOS review work. Windows evidence does not replace the still-required unlocked macOS packaged daily-loop and rollback proof, and the new session must not commit, push, publish, or weaken Happy features without separate authorization. |
| D9 | May the owning Windows Root replace and launch the installed `Happy (dev)` client for native package verification? | decided | Yes. The user explicitly authorized `安装并验证` on 2026-08-30. Authority is limited to the exact locally built unsigned Windows development candidate, the exact per-user `Happy (dev)` install/uninstall target, recoverable backup plus registry snapshot, and the repository's bounded `update-desktop` / `verify-desktop` flow. It does not authorize signing, commit, push, publication, release, official-baseline replacement, account mutation, or destructive functional testing. |
| D10 | May the owning Windows Root rebuild, replace, launch, and non-destructively inspect a new candidate containing the four TDD remediations? | decided | Yes. On 2026-08-30 the user selected `授权 Windows 重建安装验证（推荐）`. Authority covers the exact `codex-first-happy-client-windows` worktree, focused/full App checks, worktree-bound `doctor` and `build-desktop`, artifact/hash inspection, `update-desktop -DryRun`, recoverable replacement of only the per-user `Happy (dev)` target while retaining all four existing Windows backups plus the new backup, `verify-desktop`, and read-only packaged-shell inspection. It does not authorize intentional rollback execution, signing, commit, push, PR, publication, release, official-baseline replacement, login/permission/account mutation, Agent execution, message submission, or protected auth/sync/protocol/Server/Machine RPC changes. |
| D11 | Which platform owns the current complete acceptance, and what runtime validation is now authorized? | decided | The user's persistent Goal on 2026-08-30 supersedes D3, D4, D5, D8, and D10 wherever they made macOS acceptance a prerequisite or limited Windows to read-only inspection. The current installed native Windows Codex Desktop is the owning UI/IA/interaction reference, and the packaged Windows `Happy (dev)` client is the complete daily-use acceptance target. Matched Codex/Happy capture must use the same logical size, theme, and representative state; Windows must cover navigation, home, New Session, conversation, Composer, tools, permissions/questions, search, command palette, panels, Settings, responsive behavior, light/dark, keyboard/accessibility, install/reinstall safety, and a bounded real daily-use loop. Ordinary reversible in-client actions needed for that loop are authorized through existing product semantics, using isolated or non-destructive data where practical. Stop before changing authentication, authorization or permission payloads, sync/Server/Machine RPC/Session protocols, data migration, public release/signing, official-baseline replacement, or executing a destructive rollback. No commit, push, PR, or publication is authorized. Windows evidence is not macOS evidence; macOS native adaptation and acceptance are deferred to later work and do not block this Windows Goal. |
