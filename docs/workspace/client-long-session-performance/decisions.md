# Decisions: `client-long-session-performance`

| ID | Question | Options and constraints | Status | Decision/evidence |
| --- | --- | --- | --- | --- |
| D1 | What delivery boundary owns the work? | Official upstream, personal `dev`, or both. The live app and existing bounded-state optimizations are personal-client behavior; publication is not authorized. Owner: user. Reversible: yes. Cost of wrong base: duplicated work and merge conflicts. | resolved | Target the current `quiet-forest` worktree from personal `dev`; keep focused seams upstream-friendly, but do not create an upstream PR. |
| D2 | How should draft persistence become incremental? | New per-Session MMKV keys, a new Zustand draft slice, or reuse the existing module-owned `sessionDrafts` snapshot. Persistence migration and broad caller churn are unnecessary. Owner: implementation. Reversible: yes. Cost of wrong choice: stale or lost local drafts. | resolved | Keep the `session-drafts` format, make the existing snapshot authoritative, add normalized no-op behavior, and patch only the affected Session/row projection. Current source already loads this snapshot at storage creation. |
| D3 | How should streaming updates be batched? | Immediate drain, microtask-only batching, or a bounded frame window. The composer needs main-thread relief without visible lag or lock starvation. Owner: implementation. Reversible: yes. Cost of wrong window: input jank or delayed messages. | resolved | Coalesce per Session for 24 ms, cap presentation delay at 32 ms, wait outside `AsyncLock`, preserve FIFO, and bind timers to cache generation/lifecycle. Happy PR #1452 and VS Code PR #328926 support this direction. |
| D4 | How should full message sorting be removed? | Keep sorting after batching, mutate Zustand snapshots, or introduce a focused ordered collection seam. `createdAt` is immutable by reducer contract, but selector identity must remain correct. Owner: implementation. Reversible: yes through a diagnostic fallback. Cost of wrong design: ordering corruption or stale selectors. | resolved | Use a focused incremental ordered collection with a development-only full rebuild on detected invariant violation; never mutate prior Zustand snapshots. |
| D5 | How should a visible Session release heavy history? | Leave it unbounded, slice live structures in place, redesign the protocol, or stage a fresh latest tail and atomically swap at a safe idle boundary. Existing hidden eviction does not help a Session kept open for hours; durable server history is authoritative. Owner: implementation with user acceptance. Reversible: yes. Cost of wrong design: missing messages, broken tool joins, or scroll jumps. | resolved | Use count/byte hysteresis and a staged latest-tail rebuild. Swap only at the live tail with no queue/send/permission/tool/target/composition activity and unchanged generation/highest seq. Abort without mutation on any uncertainty. |
| D6 | Does this task change protocol or cross-device behavior? | Add bidirectional cursor protocol now, or remain client-only. Existing `before_seq` latest/older paging is sufficient for a contiguous head discarded by a safe tail rebase. Owner: user/repository risk gate. Reversible cost of protocol work is high. | resolved | No protocol, server, persistence migration, encryption, or cross-device change. Any newly proven protocol need returns to planning and triggers a separate decision/risk workflow. |
| D7 | How should rollout be controlled? | One broad rewrite, hidden feature flag, or independently reversible slices plus packaged evidence. Owner: user. Reversible: yes. Cost of wrong rollout: hard-to-isolate regressions. | resolved | Land draft, batching, ordered collection, and visible-tail work as serial reviewable slices. Tail rebase is enabled only after deterministic checks, review, and packaged macOS acceptance; installation/commit/push remain separately authorized. |
